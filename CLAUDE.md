## ▶️ Running the bot (start / stop) — read this first

The bot runs locally on the Mac Studio at `/Users/jefftian/JulyBot`. All commands below are run from the repo root. The DB is remote (Supabase); there is nothing local to start or stop.

**Start (foreground — for debugging, logs to terminal, Ctrl-C to stop):**
```bash
./deploy/start.sh          # == .venv/bin/python main.py
```

**Start (background — launchd agent, auto-starts on login, restarts on crash):**
```bash
./deploy/install-service.sh
```

**Stop the background service:**
```bash
./deploy/stop.sh           # boots out the launchd agent com.julybot
```

**Restart the background service after a code change:**
```bash
./deploy/install-service.sh   # re-installs + kickstarts; safe to re-run
```

**Remove the launchd agent entirely:** `./deploy/uninstall-service.sh`

- Foreground vs. background are mutually exclusive — if the launchd service is running, stop it before `start.sh` or you'll get two bots double-posting.
- Background logs: `logs/julybot.stdout.log` and `logs/julybot.stderr.log`.
- launchd label is `com.julybot`; inspect with `launchctl print gui/$(id -u)/com.julybot`.
- First-time only: `./deploy/setup.sh` (venv + `.env`), then `.venv/bin/python scripts/init_db.py` (creates tables). `init_db.py` and `create_tables` are idempotent — safe to re-run after adding tables/columns.

## Project at a glance

A Clash of Clans Discord bot, Python 3.11+. Core modules: `base_finder` (image recognition pipeline over YouTube VODs), `legend_tracker` (CoC API polling + daily snapshots), `account_linker` (Discord ID <-> CoC tag verification), `ping_automator` (APScheduler jobs), plus `x_monitor`, `youtube_feed`, `moderation`, and `roster` (admin-managed player groups + clan leave/rejoin watcher — see the 2026-07-20 entry). Discord layer (`discord_bot/`) is a thin shim — every Cog command must delegate to module functions and format the reply, nothing more.

Storage is PostgreSQL with the `pgvector` extension. Connection is raw `asyncpg` — **do not introduce SQLAlchemy or any other ORM**.

## Hard rules (do not violate without asking)

1. **Config is centralized.** Every env var read goes through [config/settings.py](config/settings.py). No `os.getenv` or `load_dotenv` calls anywhere else. If you need a new setting, add it to `Settings`, `.env.example`, and the README env-var table.
2. **Discord stays thin.** Cogs in [discord_bot/commands/](discord_bot/commands/) call module functions and format embeds. They never query the DB, hit external APIs, or do CV work directly.
3. **Modules stay independently testable.** Every async function in `modules/` must be callable with a real or mocked `asyncpg.Pool` — no implicit dependency on a running Discord bot or scheduler.
4. **Discord client is `disnake`, not `discord.py`.** The two are API-incompatible at the Cog layer.
5. **Raw SQL only.** All DDL lives in [database/models.py](database/models.py); ad-hoc queries use `pool.acquire() / conn.fetch / conn.execute`. No query builders.
6. **No hardcoded magic numbers.** Thresholds, intervals, and sizes are either in [config/settings.py](config/settings.py) or named module-level constants at the top of the file (see e.g. [modules/base_finder/detector.py](modules/base_finder/detector.py)).
7. **Logging via `logging.getLogger(__name__)`.** No `print()` outside [scripts/init_db.py](scripts/init_db.py) (which is a CLI entrypoint).
8. **Never commit `.env`** — only `.env.example`. The `.gitignore` already excludes it; don't weaken that.

## Testing

- Test runner: `pytest` + `pytest-asyncio` (strict mode).
- [tests/conftest.py](tests/conftest.py) sets dummy env vars before any project import. **This is required** because `config.settings` raises on missing required vars at import time. If you add a new required env var to `Settings`, add a matching `os.environ.setdefault` line to `conftest.py`.
- DB is mocked via `MagicMock` + `AsyncMock` and a small `_FakePoolAcquireCtx` helper. See [tests/test_account_linker.py](tests/test_account_linker.py) for the pattern; reuse it.
- HTTP calls are mocked with `unittest.mock.patch.object(module, "fn", AsyncMock(...))`. Never make real CoC API or YouTube calls in tests.
- Run: `python -m pytest tests/ -v`. As of last run: 9 passed in ~10s.

## Adding a new feature

Default workflow:

1. Add the data model (table or column) to [database/models.py](database/models.py) as a `CREATE TABLE IF NOT EXISTS`. Bump nothing else — `init_db.py` is idempotent.
2. Implement the business logic as plain async functions in the relevant `modules/<x>/` package. Keep functions narrow and pool-arg-first: `async def thing(pool, ...)`.
3. Add unit tests with mocked pool/HTTP under `tests/`.
4. Only after the module logic lands cleanly, wire a Cog command in `discord_bot/commands/`. The Cog should be 5-15 lines per command: parse args, call module function, format reply.
5. If the work is recurring, register a job in [modules/ping_automator/scheduler.py](modules/ping_automator/scheduler.py).

## Things that bit us / known gotchas

- **`config.settings` raises at import time.** Tests rely on `conftest.py` to stub vars. Don't move the `_load()` call inside a function — other modules use the eager singleton.
- **`signal.SIGTERM` isn't supported on Windows.** [main.py](main.py) wraps `loop.add_signal_handler` in a `try/except NotImplementedError`. If you refactor shutdown, preserve that fallback.
- **`pgvector` requires a Postgres extension.** `init_db.py` runs `CREATE EXTENSION IF NOT EXISTS vector;` at the start of `create_tables`. On Supabase the `postgres` role has this privilege, so it just works on first run.
- **The DB is Supabase (hosted), not local.** `DATABASE_URL` is a Supabase **Session pooler** string with `?sslmode=require`. asyncpg + Supabase's pooler can't use prepared-statement caching, so [database/connection.py](database/connection.py) creates the pool with `statement_cache_size=0` and strips that param from the DSN — **don't remove either.** `scripts/init_db.py` reuses that same `get_pool()`; don't make it open its own raw pool.
- **`data/` is gitignored except for `data/bases/.gitkeep`.** Don't add tracked files under `data/` — generated images live there.
- **APScheduler `create_scheduler(pool)` takes the pool.** The original spec showed a no-arg signature, but jobs need the pool, so it's passed at construction. If you ever need other long-lived deps in jobs, do the same — don't reach for globals.

## 2026-07-21 — /purgeword (moderation)

- Added `modules/moderation/purge.py` — `purge_user_messages(guild, target, word, moderator)` deletes every message from `target` whose content contains `word` (case-insensitive substring) across all text channels + active threads the bot can `read_message_history` + `manage_messages`. Returns a `PurgeResult` dataclass (deleted / channels_scanned / channels_skipped / failed). Pool-free — it only touches the Discord API, so tests mock disnake objects, not a pool.
- **Discord has no "all messages by user" endpoint.** The only way is to walk each channel's `history()` and filter by author — inherently slow and rate-limited. The `/purgeword` cog command therefore `defer(ephemeral=True)`s before scanning.
- **14-day bulk-delete rule:** messages younger than `BULK_DELETE_MAX_AGE_DAYS` are batched via `channel.delete_messages` (max 100/call); older ones must be deleted one at a time (Discord forbids bulk on >14d). `INDIVIDUAL_DELETE_DELAY_SECONDS` now defaults to **0** — disnake's HTTP layer already waits out rate limits, so the old 0.5s pause just slowed the trickle of old-message deletes (~2/sec → ~5/sec) without preventing 429s. Old-message-heavy runs are the slow path by nature; ~5/sec is Discord's ceiling for single deletes.
- **`MAX_DELETIONS_PER_RUN = 500` caps *deletions*, not messages scanned.** The cap check sits after the author + word filter, so non-matching messages never consume the budget. When hit, `PurgeResult.capped=True` and the cog tells the user to re-run; because deleted messages vanish from history, the next run's newest-first scan resumes past them (no re-deletion). Trade-off: each run re-*reads* history from the top — reads are cheap/unthrottled, so we accepted it over a `before`-timestamp resume param.
- Extended `logging.py` `Action` literal + colour/title maps with `"purge"`. Admin-only (`default_member_permissions`). No new tables or env vars.
- **Self-target allowed:** the command has no "can't purge yourself" guard — an admin can purge their own messages.
- **Members intent required.** `intents.members = True` in [discord_bot/bot.py](discord_bot/bot.py); the "Server Members Intent" portal toggle must also be ON or the bot won't start (`PrivilegedIntentsRequired` at login).
- **"The application did not respond" on other members:** symptom of the handler never acking. The `member` arg is typed `disnake.User` (not `Member`) so resolution can't fail on a member-vs-user mismatch or a target who left the guild. The cog also defers first, catches **all** exceptions (not just `ModerationError`), `logger.exception`s the traceback to stderr, and replies via a `_respond` helper that works pre- or post-defer — so a failure surfaces as a visible message instead of a silent timeout. If it recurs, the traceback is now in `logs/julybot.stderr.log`.
- **Concurrent channel scan (the real speedup).** The trickle was never the deletes — it's the per-channel `history()` read. Channels/threads are now scanned in parallel via `asyncio.gather`, sharing one `PurgeResult` and a `stop_event` that halts all channels once the global cap is reached. `SCAN_CONCURRENCY = None` (unbounded) by default; set it to an int to bound parallelism via a semaphore if unbounded scanning trips Discord's *global* rate limit. Concurrency means the cap can overshoot by up to ~(channels-1) batches — acceptable, never under-deletes or loops.

## 2026-08-25 — /group: Ranked Battles tournament group dashboard

- New `modules/ranked_tracker/` (`poller.py` + `group.py`) and Cog `ranked_commands` (`RankedCommands`), loaded live in `COG_MODULES`. `/group <player_tag>` looks up the CoC **Ranked Battles** weekly 100-player tournament group a player is currently in and posts a refreshable embed: a histogram of defenses received this week per member, and the last 10 defenses across the group. **Refresh-on-demand only — no polling, no DB table, no stored history.** Every refresh re-fetches live from the CoC API; both the initial command and the refresh button call the same `group.build_group_dashboard()` pipeline so they can never drift apart.
- **Ranked Battles (Oct 2025 update) is not documented on the rendered developer portal** (it's a JS SPA; an OpenAPI mirror we checked predates the update). The API shape here was reverse-engineered from `clashofclans.js`'s TypeScript source and ClashPerk's production `ranked-battle-log.ts` — both actively maintained through the update, so treated as reliable, but **unverified against a real live response**. If `/group` errors in production in a way that looks like a schema mismatch, suspect the field names below first.
- Confirmed fields: `GET /players/{tag}` now returns `leagueTier {id, name, iconUrls}`, `trophies` (now **is** the ranked trophy count — the old separate trophy system was removed), and `currentLeagueGroupTag` / `currentLeagueSeasonId` (+ `previous*`). `GET /leaguegroup/{groupTag}/{seasonId}` (note: NOT `/clans/.../currentwar/leaguegroup`, which is the unrelated older CWL endpoint) returns `members[]` (tag/name/clan/`leagueTrophies`/attack-win-loss/defense-win-loss counts) and `attackLogs[]`/`defenseLogs[]` (`opponentPlayerTag`, `opponentName`, `stars`, `destructionPercentage`, `trophies`, `creationTime`).
- **Unresolved and load-bearing: whether `defenseLogs[]` covers the whole ~100-player group or is scoped to just the tag used in the URL path.** Neither source confirms this either way. `group.detect_log_scope()` resolves it at runtime per-request by reconciling log *volume* (not tag identity — both scopes show many distinct attacker tags, so identity isn't diagnostic) against `sum(defenseWinCount + defenseLoseCount)` for the whole group vs. just the queried member. Ambiguous cases fail safe to `PLAYER_SCOPED` (the more conservative label) and `logger.warning` the raw counts — check `logs/julybot.stderr.log` for `"Ambiguous ranked defense-log scope"` after real usage to see which branch actually fires, and tighten `_SCOPE_MATCH_TOLERANCE` (currently 0.3) once real data confirms which case is which. **Do not delete `detect_log_scope` or hardcode a scope** without first confirming from real API responses — the whole point is to never silently present player-scoped data as if it were group-wide.
- `compute_defense_histogram()` buckets every member by `defenseWinCount + defenseLoseCount`, sorted highest-first, and deliberately **includes a 0-defenses bucket** if any member has zero — omitting it would make bucket counts fail to sum to the group size.
- The `/group` refresh button (`RankedGroupView`) is **deliberately non-persistent** (`disnake.ui.View(timeout=None)`, no `custom_id`-based state, no `register_persistent_views` hook, no DB row backing it). Unlike `/postbase`'s buttons, which must survive bot restarts indefinitely, this dashboard only needs to work while the invoker is actively looking at it — reading `self.coc_tag` off the view instance is safe here specifically because a non-persistent view is never re-dispatched to a different registered instance (the failure mode `/postbase` had to design around). If this ever needs to survive restarts, revisit that decision rather than assuming it still holds.
- `modules/ranked_tracker/poller.py` is its own small CoC API client (own `aiohttp.ClientSession`, own `get_session()`/`close_session()`) rather than an addition to `legend_tracker/poller.py` — same reasoning that keeps `x_monitor/client.py` and `youtube_feed/fetcher.py` as separate HTTP layers per feature. `close_session()` is registered in `main.py`'s shutdown block alongside the other module sessions.
- Reuses `modules.account_linker.linker._normalize_tag` (imported as `normalize_tag`) for CoC tag cleanup — the same cross-module import-aliasing precedent already used in `modules/roster/storage.py`. No new shared-utility module was introduced.
- No new `config/settings.py` fields — reuses `COC_API_TOKEN` / `COC_API_BASE_URL` as-is. No new DB table.
- Tests: `tests/test_ranked_tracker.py` (17 cases), HTTP-mock-only (no pool involved), covering the histogram, both `detect_log_scope` branches plus the ambiguous fallback, timestamp parsing of the CoC `"20260825T142530.000Z"` format (`_parse_coc_timestamp`, not the epoch-ms format `x_monitor/snowflake.py` uses), and an end-to-end `build_group_dashboard` smoke test.
- **Confirmed live (2026-08-25): `GET /leaguegroup/{groupTag}/{seasonId}` requires a `playerTag` query parameter — it 400s `"Required parameter 'playerTag' missing"` without it.** The `clashofclans.js` typing this was reverse-engineered from marks `playerTag` optional (`options?: OverrideOptions & { playerTag?: string }`), which is simply wrong for this endpoint; don't trust that typing on this point. `poller.get_league_group(group_tag, season_id, player_tag)` now takes it as a required positional arg — always pass the tag whose group membership is being queried. Also: `get_league_group` no longer returns `None` on failure like the rest of this repo's CoC pollers — it raises `poller.LeagueGroupFetchError(status, body)` instead, specifically so `/group`'s error message can show the real HTTP status/body inline in Discord rather than a generic failure hidden behind a log line the operator may not have access to. If you add more calls to this endpoint, keep that raise-with-detail behavior; don't quietly revert it to the None-on-failure convention used elsewhere.
- **`is_likely_to_be_hit_next()` (2026-08-25):** a per-player "likely to be hit next" heuristic based on the user's own description of how the matchmaker behaves (not from any documented API behavior — this is a gameplay inference, not a confirmed rule). It flags the *queried* player only (not the whole group) when their own defense count is below the group's mode (majority) defense count, AND the pool of members at-or-below that count is smaller than `LOW_DEFENSE_POOL_THRESHOLD` (currently 40, a tunable constant, not derived from group size or remaining attacks). Rationale given: the matchmaker seems to keep defenses received roughly even, so a small pool of below-majority members becomes an increasingly likely target for the attacks still left in the week. Rendered as a warning line appended to the "Defenses Received This Week" embed field, only when true — no separate section, and never flags anyone but the player the command was run for.
- **Three-state, not boolean (fixed same day):** the first version returned a plain bool and rendered nothing when `False`, which in real usage (early in the tournament week, when the histogram only spans 2-3 closely-packed buckets and nobody has dropped below the mode yet) meant the flag *always* silently rendered nothing — indistinguishable from the feature being broken or skipped. `is_likely_to_be_hit_next()` now returns one of `LIKELY_TARGET` / `NOT_FLAGGED` / `UNKNOWN` (module-level constants in `group.py`), and `build_group_embed` always renders a line for the first two ("⚠️ Likely to be hit next." / "✅ Not currently a likely target.") — only `UNKNOWN` (queried player not found in `members`, or an empty group) renders nothing, since there's genuinely no status to report there. Don't revert this to a bool; the silent-neutral-state confusion is exactly what this fixed.

## 2026-08-25 — /groupextrapolate: 30-attack pace projection, per-member fan-out

- New `modules/ranked_tracker/extrapolate.py` + `/groupextrapolate <player_tag>` in `ranked_commands.py`. ## 2026-08-29 — Stripe subscription website (`web/` package)

- New top-level `web/` package: a FastAPI + uvicorn website offering paid monthly subscription tiers via Stripe Checkout (pricing page → Checkout Session → webhook records the result). **Runs as its own OS process, not merged into `main.py`'s bot lifecycle** — own entry point ([web/main.py](web/main.py)), own launchd service (`com.julybot.web`, [deploy/com.julybot.web.plist.template](deploy/com.julybot.web.plist.template)), own start/stop/install/uninstall scripts (`deploy/*-web.sh`), own log files (`logs/julybot-web.{stdout,stderr}.log`). Installing, restarting, or removing the bot's service has zero effect on the website's, and vice versa — an operator managing this box needs to run **two** independent services now, not one.
- Both processes share [config/settings.py](config/settings.py) and [database/connection.py](database/connection.py)'s `get_pool()`/`close_pool()` singleton pattern, but **never the same running pool instance** — each process calls `get_pool()` itself and gets its own pool inside its own event loop. `web/app.py` wires this through FastAPI's `lifespan` context manager (open on startup, close on shutdown) rather than `main.py`'s manual asyncio signal-handler wiring, since uvicorn already owns the event loop.
- **Scope of this pass is deliberately narrow: checkout + webhook plumbing only. No Discord role granting on subscribe/cancel** — that's an explicit follow-up. The `subscriptions` table already has a nullable, unpopulated `discord_id BIGINT` column reserved for it, so that future pass needs no migration, only logic. The pricing page also collects an **optional, unverified** "Discord username" text hint (passed through as Stripe Checkout `metadata.discord_username`, stored in `discord_username_hint`) — cosmetic only in this pass, not validated against a real Discord account.
- **Two tiers today:** `l2_l3` ("L2/L3", $20/month) and `l1` ("L1", $30/month, the higher tier) — see [web/tiers.py](web/tiers.py). Tier display copy (name/price/description) is a Python constant; the Stripe Price ID per tier is a named setting (`STRIPE_PRICE_ID_L2_L3`, `STRIPE_PRICE_ID_L1`), not a CSV list or DB table. Deliberate trade-off: adding/renaming a tier needs an `.env` change plus a small code change plus a deploy, in exchange for typo-safety and matching this repo's existing settings.py convention (structural/code-adjacent config as constants, not admin-editable DB rows) — reconsider if tiers start changing often enough that a deploy per change becomes painful.
- **Idempotency is via upsert, not an event-log table.** `modules/subscriptions/storage.py`'s `upsert_from_checkout` does `INSERT ... ON CONFLICT (stripe_subscription_id) DO UPDATE`, so a redelivered `checkout.session.completed` webhook (Stripe retries on anything but a 2xx, and can also just duplicate-deliver) re-applies the same state instead of erroring or duplicating a row. `upsert_from_stripe_subscription` (backing `customer.subscription.updated`/`.deleted`) is an `UPDATE ... WHERE stripe_subscription_id = $1`, returning `None` if the row doesn't exist yet — logged as a warning rather than treated as fatal, since it just means an out-of-order delivery arrived before the row-creating `checkout.session.completed` did. Accepted risk: no protection against genuinely out-of-order same-subscription updates overwriting newer state with older — Stripe's own delivery ordering is "best effort," and a stronger guarantee would need a proper event log, judged not worth the complexity for v1.
- **Stripe's Python SDK is synchronous.** Every SDK call is isolated in [web/stripe_client.py](web/stripe_client.py) — the only module that imports `stripe` — and wrapped in `asyncio.to_thread(...)` so a blocking network call never stalls the FastAPI event loop. Any new Stripe API call added later must follow the same pattern. `stripe.error.SignatureVerificationError` and payload-parsing `ValueError`s are both translated into one typed `WebhookSignatureError` so the webhook route doesn't need to import `stripe` itself.
- **The webhook route reads the raw request body before any JSON parsing.** Stripe's `stripe.Webhook.construct_event` signature check needs the exact bytes Stripe sent (`await request.body()`), so [web/routes/webhook.py](web/routes/webhook.py) must not use a FastAPI dependency or model that parses JSON first — that would consume/alter the body and break verification. A bad/missing signature returns 400; every *handled* event type (`checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`) and every *unhandled* one both return 200 — acking unhandled types on purpose so Stripe doesn't retry-storm the endpoint over events we don't act on.
- **Public reachability (domain, TLS, port-forwarding) is explicitly out of the app's scope** — `WEB_BASE_URL` just needs to be set to whatever the real public URL ends up being, since it's used to build the Checkout `success_url`/`cancel_url`. See [deploy/README.md](deploy/README.md) for the recommended path (buy a domain, port-forward 443 through the router, terminate TLS with something like Caddy in front of uvicorn) and the Stripe CLI (`stripe listen`) for local webhook testing without any of that.
- New dependencies: `fastapi`, `uvicorn[standard]`, `jinja2`, `python-multipart`, `stripe` (added to `requirements.txt`). `python-multipart` is needed because the pricing page's optional Discord-username field is a real HTML form POST (not a query string), to avoid leaking it into server logs/referrers.
- Tests: [tests/test_subscriptions_storage.py](tests/test_subscriptions_storage.py) (mocked-pool pattern, same `_FakePoolAcquireCtx` helper as `test_roster.py`), [tests/test_stripe_client.py](tests/test_stripe_client.py) (patches the real `stripe` SDK's module-level functions, verified against the actually-installed `stripe` 15.x package rather than assumed), and [tests/test_web_routes.py](tests/test_web_routes.py) (FastAPI `TestClient`, everything mocked — pricing page rendering, checkout redirect + metadata, webhook signature failure, all three handled event types, idempotent-replay-doesn't-error, and an unhandled event type still returning 200).

Two new one-time Prices (same $20/$30 amounts, no billing interval) had to be created in the Stripe Dashboard and `.env`'s `STRIPE_PRICE_ID_L2_L3`/`STRIPE_PRICE_ID_L1` repointed at them. Idempotency now keys on `stripe_checkout_session_id` (always present, unique per checkout attempt) instead of `stripe_subscription_id` (which doesn't exist here). `status` now mirrors Stripe Checkout's `payment_status` field (`paid`/`unpaid`/`no_payment_required`) rather than a subscription-lifecycle status.
- **Confirmed with the user: one row per purchase, not one row per customer.** The same buyer purchasing in August and again in September produces two separate rows — `modules/subscriptions/storage.py`'s `upsert_from_checkout` still upserts (idempotent against webhook redelivery of the *same* checkout), but a genuinely new checkout session always inserts a new row. ## 2026-08-30 — /subscribe is a ticket purchase flow with admin confirmation

- **`/subscribe <member>` is admin-only and posts publicly** in the invoking channel, replacing the ephemeral self-serve version from earlier the same day. Purchases happen in a private ticket where a moderator is already present, and they need to see how far along the buyer is — an ephemeral message is invisible to them. One message is edited in place through **pending → signed → confirmed** (or cancelled), so the ticket carries a single running record rather than a pile of messages.
- **The gates are checked against the DB row, not the view.** Only `buyer_id` can click I Agree; only an admin (administrator or manage_guild) can Confirm or Cancel. A persistent view outlives the process, so in-memory state is never trustworthy.

- **The row is created *before* the message is posted** (`create_pending_agreement`), because the persistent view's `custom_id`s need an agreement id to encode. That reinstates a pending state which the previous pass had removed — correct here for a different reason than the original `/agreement send` had it. If `channel.send` fails the row is deleted, so no orphan points at a message that never existed (same rollback as `/postbase`).
- **`custom_id` scheme is `purchase:<action>:<agreement_id>` and `_id_from(inter)` parses the id off the clicked button — never read `self.agreement_id` in a callback.** A persistent view is matched by custom_id but dispatched to whichever registered instance disnake picks, so the instance's id is usually a *different* purchase's. This is the exact bug `/postbase` hit (see the 2026-08-06 entry); there's a regression test for it in `test_subscribe.py`.

- **Guards live in SQL, not only in handlers**: `confirm_agreement` requires `signed_at IS NOT NULL AND confirmed_at IS NULL AND voided_at IS NULL`, and `sign_agreement` gained `voided_at IS NULL` so a buyer can't sign a purchase an admin cancelled while they had the message open. Double-clicks are no-ops because only the first UPDATE returns a row.
- `register_persistent_views` is back in `bot.py`'s `on_ready`, now pointing at `subscribe_commands` (the agreements one was deleted a pass earlier). `list_views_to_restore` skips confirmed and voided rows — those are terminal and their buttons are already dead.
- `/agreement` is now read-only (`lookup`, `receipt`) and surfaces the confirmed state through `lookup_embed` / `receipt_text`. Both still render historical moderator-flow rows *and* the new shape; that dual support is the thing most likely to regress and is covered in `test_agreements.py`.

## 2026-09-04 — /purchases: review recorded purchases and fix a mislink

- **A mislinked payment was previously unfixable from Discord.** If an admin picked the wrong payment out of the Stripe dropdown when confirming, the unique index on `stripe_subscription_id` then stopped the *correct* buyer ever being linked to it, and the only remedy was editing Supabase by hand. `/purchases relink <id>` fixes that.

## 2026-09-04 — /purchases archive: month close-out, and the one-time access gap it closes

- **`ACTIVE_STATUSES` was `("active", "trialing")` — Stripe *subscription* statuses only, so a one-time purchase (`succeeded`) never counted as active.** With the Payment Links currently one-time, `list_active_subscribers` would have returned nothing for every real buyer. `"succeeded"` is now included, which makes the archive flag load-bearing rather than cosmetic: a one-time payment's status **never changes**, so without archiving it would grant access forever.

- **`archive_subscribers` only touches rows where `archived_at IS NULL`**, so re-running is a no-op rather than restamping the timestamp and losing when the close-out actually happened. It returns the affected rows so the Cog can report a count.
- **The command previews and confirms before writing** (`ArchiveConfirmView`): it's bulk, and easy to fire against the wrong month. The preview lists who is affected and states plainly that rows stay in the log.
- **`created_at` comes back from asyncpg as a naive TIMESTAMP** (Supabase runs UTC), so the cutoff is stripped of tzinfo before comparison — `_naive()` in the Cog. Comparing aware to naive raises `TypeError`.
- **`/purchases list` is paged** (`PAGE_SIZE = 10`, `LIST_LIMIT = 200`): a month can carry ~100 purchases and the row you want is rarely in the newest handful. Records are held on the view and paged in memory rather than re-queried per click, so the page can't shift under the reader mid-scan. Paging buttons are only attached when there's more than one page. `build_list_embed` clamps an out-of-range `page`, so a stale click after the list shrank renders the last page rather than a blank one.
